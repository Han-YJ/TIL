# 캐시가 오히려 느려질 때

캐시는 공짜가 아니다. **만드는 비용(압축·업로드)과 푸는 비용(다운로드·해제)** 이 있고, 그 합이 캐시가 없앨 시간보다 크면 캐시를 두는 쪽이 느리다.

## 실제로 겪은 사례

어떤 모노레포 CI 의 의존성 캐시가 오래 전부터 동작하지 않고 있었다. 로그가 이랬다.

```
Cache "deps": Downloading
Cache "deps": Not found            ← 받을 게 없음
...
Assembling contents of new cache 'deps'
Cache "deps": Skipping upload for empty cache   ← 올릴 것도 없음
```

원인은 경로였다. 패키지 매니저가 스토어를 **프로젝트와 같은 파일시스템**에 두려 하는데(하드링크를 쓰기 때문), 선언한 캐시 경로는 다른 마운트에 있어서 실제 스토어가 거기에 생기지 않았다. 선언 경로는 끝까지 빈 채로 남았다.

경로를 고정하자 캐시는 정상 동작했다. 그리고 숫자가 드러났다.

| 항목 | 시간 |
|---|---|
| 의존성 설치 전체 (1,100여 패키지 새로 받음) | **17.4초** |
| 캐시 압축 | **76초** |
| 캐시 업로드 (267 MiB) | 2초 |

**캐시를 만드는 비용이 없앨 비용의 4.5배였다.** 적중한 다음 런에서도 267 MiB 를 받아 푸는 시간이 들고, 설치가 0이 되지도 않는다(스토어에서 링크하는 시간은 남는다).

그래서 **고친 것을 되돌리고 캐시 선언 자체를 걷었다.** 측정 근거는 설정 파일 주석에 남겨, 다음 사람이 같은 진단으로 또 「고치려」 들지 않게 했다.

## 배운 것

- **「캐시가 미스난다」는 문제 서술이지 개선 근거가 아니다.** 개선 근거는 「캐시가 없앨 시간 > 캐시를 만들고 푸는 시간」이다
- 병목부터 확인한다 — 위 사례에서 설치는 전체 스텝(약 8분)의 **4.5%** 였다. 애초에 여기가 병목이 아니었다
- 로그의 「1,100개를 새로 받는다」 같은 **개수**는 비용을 말해 주지 않는다. **초**를 읽어야 한다
- 압축 시간은 캐시 크기에 비례한다. 수백 MB 를 넘어가면 압축만으로 원래 작업보다 오래 걸리는 구간에 쉽게 들어간다

## 캐시를 둘 만한 조건

- 원래 작업이 **충분히 무겁다** (수십 초~분 단위)
- 캐시 크기가 작거나, 압축이 이미 된 형태다
- 적중률이 높다 (매번 무효화되는 키를 쓰지 않는다)
- 만드는 비용이 **매 런이 아니라 가끔** 든다 (대부분의 CI 캐시는 존재하면 재사용하고 주기적으로만 다시 만든다)
