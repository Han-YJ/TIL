# CI 최적화 회고 — 건너뛰기에서 영향 범위, 그리고 기준선까지

프론트엔드 모노레포(Next.js 앱 + 디자인 시스템 패키지 + Storybook)의 CI 를 단계적으로 다듬었다. 단계마다 다룬 비용의 축이 달랐고, 축이 바뀔 때마다 던지는 질문도 바뀌었다. 그 순서대로 정리한다.

CI 는 Bitbucket Pipelines 이고, 과금 단위는 **스텝이 돈 시간의 합(빌드 분)** 이다. 스텝마다 컨테이너를 띄우고 clone·install 하는 준비 시간이 따로 든다(이 환경에서 스텝당 약 100초).

## 1. 「이 PR 에서 이 검사를 돌릴 필요가 있나」 — 경로로 건너뛰기

처음 손댄 건 **안 돌려도 되는 걸 건너뛰는 것**이었다. Bitbucket 의 `changesets` 조건은 PR 이 바꾼 경로를 보고 스텝을 아예 띄우지 않는다.

```yaml
- step:
    <<: *step-a11y
    condition:
      changesets:
        includePaths: ['packages/ui/src/**', 'packages/tokens/src/**', 'apps/storybook/**', 'pnpm-lock.yaml']
```

- 디자인 시스템을 안 건드린 PR 은 Storybook 빌드 + 접근성 검사(약 9분)를 건너뛴다
- 문서·도구 설정(`.claude/**`·`docs/**`·`*.md`)만 바꾼 PR 은 아무 스텝도 안 돈다

조건 경로는 **검사 결과에 실제로 닿는 범위**로 맞춘다. 패키지 메타데이터(`package.json` 의 `exports` 등)는 렌더를 바꾸지 않으므로 `packages/ui/**` 가 아니라 `packages/ui/src/**` 로 잡았다.

다만 이 조건은 **돌리느냐 마느냐** 둘 중 하나다. 디자인 시스템 파일 하나만 바꿔도 스토리 64개를 전부 돌린다. 이 한계가 4장의 출발점이 된다.

## 2. 「기다리는 시간인가, 돈인가」 — 병렬화의 두 얼굴

검사(포맷·타입·린트·유닛)를 한 스텝에 이어 붙였더니 PR 대기가 **합**(559초)이 됐다. 서로 독립이라 병렬 스텝으로 나눴고, 대기 시간은 **가장 긴 스텝 하나**로 줄었다.

여기서 처음 구분하게 된 게 두 숫자다.

| | 무엇이 정하나 |
|---|---|
| PR 대기 시간 (체감) | 병렬 스텝 중 **가장 긴 것** |
| 빌드 분 (과금) | 스텝 시간의 **합** — 준비 시간 포함 |

병렬화는 대기 시간을 줄이는 대신 과금을 늘린다. 스텝마다 준비 시간 약 100초가 붙기 때문이다. 같은 계산으로 반대 방향도 정했다. 몇 초면 끝나는 포맷 검사는 별도 스텝으로 두면 매번 100초를 더 내므로, 타입 검사 스텝 안에서 백그라운드로 겹쳐 돌린다.

> 속도를 줄이려는지 돈을 줄이려는지 먼저 정하지 않으면, 같은 변경이 개선인지 악화인지 판단할 수 없다.

## 3. 「이 캐시가 정말 이득인가」 — 재 보고 걷어 낸 캐시

캐시는 보통 이득으로 가정하지만, 저장·복원에도 시간이 든다. pnpm 스토어 캐시가 실제로 쌓이는 경로로 맞춘 뒤 양쪽 비용을 쟀다.

- 스토어 267 MiB 압축·업로드: **76초**
- 캐시 없이 install: **17.4초**

캐시가 install 보다 4배 비싸서 걷어 냈다. 나중에 누가 「캐시가 없네」 하고 다시 붙이지 않도록, 이 숫자를 설정 파일 주석에 남겼다. 반대로 Playwright 브라우저 캐시는 실제로 적중하고 있어서 그대로 뒀다.

## 4. 「건너뛸 수 없다면, 어디까지 돌릴까」 — 영향 범위로 좁히기

경로 조건으로 걸러지지 않는 PR 은 여전히 전부를 돌렸다. 마지막으로 잰 수치는 이랬다.

| 스텝 | 시간 | 안을 쪼개 보면 |
|---|---|---|
| Storybook 접근성 검사 | 544초 | 테스트 러너 395초 — 스토리 64개 전부 |
| 앱 유닛 테스트 | 344초 | 테스트 본문 50초 · 환경 준비 229초 · import 214초 (워커 합산) |
| 디자인 시스템 유닛 테스트 | 216초 | 테스트 본문 156초 |

앱 유닛 테스트는 본문 실행이 50초뿐이다. 나머지는 **파일마다** 드는 준비 비용이라, 돌리는 파일 수를 줄이면 거의 그만큼 준다. 이 비용을 읽는 법은 [유닛 테스트가 느릴 때 import 와 environment 부터](./slow-tests-check-import-and-environment-first.md)에 정리했다.

그래서 **PR 이 바꾼 파일이 import 로 닿는 테스트만** 돌리기로 했다. 흔히 affected tests(영향받는 테스트)라고 부르는 방식이다.

### 유닛 테스트 — 도구가 해 준다

vitest 는 `--changed <기준 커밋>` 으로 바뀐 파일에서 import 그래프를 거슬러 올라가 테스트를 고른다.

```bash
git fetch origin "$BITBUCKET_PR_DESTINATION_BRANCH"
vitest run --changed FETCH_HEAD --passWithNoTests
```

- git 루트 기준으로 diff 를 잡아서, 앱 바깥(디자인 시스템 패키지, 루트 `e2e/`) 변경도 따라간다
- 홈 화면 상수 파일 하나 → 261개 중 1개 파일
- 디자인 시스템 컴포넌트 하나 → 77개 (`@acme/ui` 를 import 하는 테스트 전부)
- 고를 테스트가 0개면 `--passWithNoTests` 로 성공 처리

**함정 하나.** lockfile·`vitest.config.ts` 가 바뀌면 전부 다시 돌아야 하는데, `forceRerunTriggers` 를 설정해도 `--changed` 실행에서는 적용되지 않았다. lockfile 을 바꿔도 0개, 설정 파일을 바꿔도 0개가 골라졌다. 소스를 보니 `--changed` 는 git diff 를 그래프로 좁힐 뿐이고, `forceRerunTriggers` 는 watch 모드 쪽 장치였다. 그래서 「이 파일이 바뀌면 전체」는 vitest 에 맡기지 않고 CI 스크립트가 직접 판정하게 했다.

### Storybook — 도구가 못 해 줘서 직접 그렸다

스토리 파일은 전부 디자인 시스템의 루트 `index.ts`(모든 컴포넌트를 다시 내보내는 배럴 파일)로 import 한다.

```ts
import { DropdownSearchMenu, Button } from '@acme/ui';
```

import 그래프만 보면 모든 스토리가 배럴 하나에 닿는다. Jest 의 `--findRelatedTests` 같은 도구로는 컴포넌트 하나를 바꿔도 스토리 전부가 골라진다.

다행히 패키지 안쪽은 상대 경로 import 뿐이라 정적으로 그릴 수 있었다. 작은 스크립트로 이렇게 했다.

1. 배럴의 `export { A, type B, C as D } from './x'` 를 읽어 **이름 → 모듈 파일** 표를 만든다
2. 스토리가 배럴에서 가져온 **이름**만 그 모듈로 바꾸고, 거기서 상대 import 를 따라 닿는 파일 전부를 모은다
3. 그 집합이 PR 변경 파일과 겹치는 스토리만 고른다

모든 스토리를 감싸는 `preview.tsx`(데코레이터)의 의존은 곧 모든 스토리의 의존이다. 그래서 「preview 가 닿는 파일이 바뀌면 전체」를 조건에 넣었다. preview 가 쓰는 토스트 컴포넌트를 바꿔 전체로 바뀌는 것까지 확인했다.

결과는 컴포넌트 하나 변경 → 스토리 64개 중 9개였다. 로컬에서 테스트 러너는 8.7초에 끝났다. 같은 PR 에서 이미지를 Playwright 공식 이미지로 바꿔 브라우저 설치도 뺐다. 다만 CI 에서 줄어든 시간은 아직 재지 않았다.

## 5. 「좁히면 무엇을 놓치나」 — 안전망과 그 값

영향 범위로 좁히면 두 가지를 놓칠 수 있다.

- import 로 이어지지 않는 의존: 동적 import, 파일을 직접 읽는 테스트 등
- **PR 끼리 엇갈린 조합**: A 의 CI 가 통과한 뒤 B 가 먼저 머지되고, A 가 다시 돌지 않고 머지되면 「A+B」는 한 번도 테스트되지 않는다

사실 두 번째는 원래부터 있던 틈이었다. 메인 브랜치(develop) 머지 뒤에는 유닛 테스트를 돌리지 않고 있었다.

흔한 해법은 「PR 은 영향 범위, 메인 브랜치는 머지마다 전체」다. 그런데 실제 횟수를 세 보니 이 저장소에는 맞지 않았다.

- 9일 동안 PR 파이프라인 173회, develop 머지 126회 — PR 하나가 CI 를 평균 1.4번만 돌린다
- 머지 수가 PR 런 수에 가까워서, 머지마다 전체(+76분/일)를 돌리면 PR 에서 줄인 몫(−70분/일, 추정)을 거의 다 되돌려 쓴다

그래서 이렇게 정했다.

| 시점 | 도는 것 |
|---|---|
| PR | 영향 범위 |
| develop | **하루 한 번** 전체 유닛 (예약 실행, +6분/일) — 놓친 것을 하루 안에 잡는다 |
| main (운영 배포) | 전체 유닛 통과 뒤에만 배포 — 릴리스가 드물어 직렬로 막아도 비용이 거의 없다 |

> 「보통 이렇게 한다」는 방식이 우리 숫자에서도 이득인지는 런 횟수 비율로 확인해야 한다.

## 6. 「왜 이건 좁히고 저건 전체인가」 — 기준선을 글로 남기기

검사가 하나씩 늘면서 「영향 범위냐 전체냐」 판단이 검사별로 따로 내려져 있었다. 이 상태로 두면 다음 검사를 넣을 때마다 같은 논의를 처음부터 다시 하게 된다. 그래서 기준을 먼저 세우고, 그 기준으로 모든 검사를 다시 판정했다. 그 결과 린트와 포맷도 영향 범위로 옮겼다.

1. **영향 범위로 돈다** — 결과가 「그 파일 + 그 파일이 import 하는 것」만으로 정해지고, 도구가 그 의존을 정확히 따라갈 수 있는 검사
2. **전체를 돈다** — 프로그램 전체를 봐야 하는 검사. 또는 모든 대상에 닿는 입력(의존 버전, 도구 설정, 판정 스크립트 자체)이 바뀌었거나, 바뀐 파일을 알아내지 못했을 때
3. **안전망** — 영향 범위로 도는 검사는 주기 실행과 운영 배포 전에 반드시 전체로 다시 돈다

| 검사 | 판정 | 이유 |
|---|---|---|
| 타입 검사 (tsc) | 전체 | 한 파일 타입이 바뀌면 그걸 쓰는 다른 파일이 깨진다 |
| 린트 | 바뀐 파일만 | 타입 정보를 쓰지 않는 설정이라 규칙이 파일 단위 |
| 포맷 | 바뀐 파일만 | 파일 단위 |
| 유닛 · Storybook | import 그래프 | 위 4장 |

판정 로직은 스크립트 하나에 모았다. 「이 파일이 바뀌면 전체」 표도 검사별로 거기에 둔다. 기준선 문서에는 원칙만 적는다. 다음에 검사를 추가하는 사람은 스크립트를 고치기 전에 문서의 세 줄로 먼저 판단하면 된다.

## 하지 않은 것

- **디자인 시스템 테스트의 입력 대기 제거** (`userEvent.setup({ delay: null })`) — 무거운 5개 파일로 재 보니 테스트 시간이 22% 줄었다. 호출 404곳을 고치는 비용에 비해 작아서 영향 범위 선택으로 대신했다.
- **테스트 샤딩** — 대기는 줄지만 스텝이 늘어 준비 시간만큼 과금이 는다(2장).

## 정리

- 단계마다 질문이 바뀌었다. **건너뛸까 → 기다림인가 돈인가 → 이 장치가 정말 이득인가 → 어디까지 돌릴까 → 무엇을 놓치나 → 무엇을 기준으로 정하나.** 앞 단계를 정리해야 다음 단계의 비용이 보인다.
- 대기 시간은 가장 긴 스텝, 과금은 스텝의 합이다. 둘을 따로 본다.
- 캐시·병렬화 같은 「당연히 빨라지는」 장치도 재 보면 손해일 수 있다. 잰 숫자는 설정 옆 주석에 남긴다.
- 영향 범위는 도구가 그래프를 따라갈 때만 믿는다. 배럴 파일 하나가 그래프를 뭉개면 직접 그린다. 도구의 「이 파일이 바뀌면 전체」 장치가 그 실행 모드에서도 적용되는지 확인한다.
- 좁혔으면 안전망을 둔다. 안전망의 주기는 런 횟수 비율로 정한다.
- 검사별 판단이 쌓이기 시작하면 기준선을 글로 세우고, 모든 검사를 그 기준으로 다시 판정한다.
