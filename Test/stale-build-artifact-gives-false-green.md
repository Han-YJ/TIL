# 빌드 산출물로 테스트하면, 소스를 고쳐도 초록은 옛 코드의 것이다

테스트가 **소스가 아니라 빌드 산출물**을 상대로 돌면, 산출물은 마지막 빌드 시점의 **스냅샷**이다. 그 뒤에 고친 소스는 다시 빌드하기 전까지 **존재하지 않는다.** 그 상태로 돌린 런은 옛 코드를 검증하고 초록을 준다.

빨간 결과는 눈에 띄지만 이건 **거짓 초록**이라 더 비싸다. 초록을 받은 순간 보는 것을 멈추기 때문이다.

## 어디서 생기나 — Playwright만의 이야기가 아니다

| 실행 방식 | 진실의 출처 | 낡을 수 있는 구간 |
| --- | --- | --- |
| dev 서버 (요청 시 컴파일) | **소스** | 사실상 없음 |
| 프로덕션 빌드 후 실행 | **산출물** | 마지막 빌드 이후 고친 전부 |

같은 모양이 널려 있다.

- 번들러 산출물(`dist/`)을 임포트하는 테스트 — 소스를 고치고 빌드를 안 하면 옛 번들을 테스트한다
- **도커 이미지**를 띄워 도는 통합 테스트 — 이미지를 다시 안 말면 옛 레이어를 테스트한다
- 컴파일 언어에서 빌드 캐시가 일부만 무효화될 때
- 별도 프로세스로 띄워 둔 서버에 붙는 테스트 — 그 서버는 **띄울 때의 산출물**을 들고 있다

## 왜 하필 디버깅할 때 물리나

가장 흔한 시나리오는 이것이다.

1. 원인을 찾으려고 소스에 로그·계측을 박는다 → 빌드하고 돌린다 (여기선 빌드를 한다)
2. 원인을 찾는다
3. **계측을 지운다**
4. "깨끗해졌는지" 확인하려고 다시 돌린다 → **여기서 빌드를 건너뛴다.** 「로그 한 줄 지웠을 뿐인데」

그래서 빌드를 거르는 런이 하필 **판정용 런**이다. 3번에서 지운 코드가 4번에서 그대로 돌고, 결과는 초록이다.

## 눈치채는 법

- **지운 코드의 흔적이 출력에 남는다** — 삭제한 로그가 찍히거나, 삭제한 코드에서 난 에러가 스택에 뜬다. 실제로 이 단서가 없었으면 그냥 초록으로 믿었을 상황이 있었다
- **지금 소스로는 통과할 수 없는 단언이 통과한다** — 의심되면 반대로 확인한다. 소스에 반드시 실패할 단언(`expect(true).toBe(false)` 수준)을 넣고 돌려서 **여전히 초록이면** 그 런은 소스를 안 보고 있다는 증거다
- 빌드 시각 < 소스 수정 시각

## 구조로 막기 (강한 순)

1. **빌드와 테스트를 한 명령으로 묶는다** — `build && test`. 건너뛸 방법을 없애는 게 규율보다 강하다
2. **산출물에 빌드 식별자를 심고 런이 그걸 찍게 한다** — 헤더·전역 변수 무엇이든. 어떤 산출물을 상대했는지가 로그에 남으면 사후에 가릴 수 있다
3. **산출물이 소스보다 최신인지 하네스가 검사한다** — 소스 mtime > 빌드 mtime 이면 중단
4. **반복용 경로와 판정용 경로를 섞지 않는다** — 빠른 반복은 dev, 판정은 빌드. 어떤 결과가 어느 쪽에서 나왔는지 모르게 되는 순간 그 결과는 근거가 아니다

## 더 고약한 변종 — 살아 있는 서버 재사용

테스트 하네스가 **이미 떠 있는 서버를 재사용**하도록 설정돼 있으면(Playwright의 `reuseExistingServer` 같은), 그 서버는 **띄웠던 시점의 산출물**을 계속 들고 있다. 이때는 빌드를 다시 해도 소용없다 — 새 산출물을 아무도 안 읽는다. 함정이 런 단위가 아니라 **세션 단위로 상주**한다.

그래서 판정용 런은 서버 재사용을 끄는 편이 안전하다. 「포트가 물려 있으면 조용히 옛 서버에 붙는」 것보다 **거기서 죽는 편이 낫다.**

## 한 줄

> 초록은 "내 코드가 맞다"가 아니라 **"내가 상대한 산출물이 맞다"** 는 뜻이다. 그 둘이 같다는 것은 따로 보장해야 한다.
