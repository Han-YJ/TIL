# 신세대 LLM 프롬프팅 — "시키는 프롬프트"에서 "빼는 프롬프트"로

구세대 모델용 프롬프트에는 모델의 부족함을 메우는 보정 지시가 쌓인다: "답을 다시 한 번 검증해라", "반드시 이 도구를 써라", "3번의 툴 콜마다 진행 상황을 요약해라". 모델 세대가 올라가면 이 지시들의 상당수가 **모델이 이미 스스로 하는 행동**이 되고, 그 순간 보정 지시는 이중 실행이 되어 순수 비용(토큰·지연)으로 변한다.

## 왜 역효과가 나나

- **자기 검증** — 신세대 모델은 시키지 않아도 자기 작업을 검증한다. "검증 단계를 넣어라"는 지시가 있으면 자체 검증 + 지시된 검증이 겹쳐 과잉 검증이 된다. 결과 품질은 안 오르고 토큰만 는다.
- **지시의 문자적 준수** — 신세대일수록 지시를 더 문자 그대로 따른다. "중요한 이슈만 보고해라(be conservative)" 같은 필터 지시는 구모델에선 느슨하게 무시됐지만, 신모델은 충실히 따라서 **찾아낸 결함을 보고 단계에서 걸러버린다** — 측정 recall이 떨어지는데 실제 능력은 올라간 상태. 해법은 "전부 보고하고 필터링은 다음 단계에서"로 지시를 뒤집는 것.
- **과잉 트리거** — "CRITICAL: You MUST use this tool" 류의 강한 지시는 구모델의 소극성을 이기려던 것인데, 지시를 잘 따르는 신모델에선 과잉 트리거를 만든다. 톤을 낮추는 게 수정 방향.

## 층위를 구분해야 한다 — 프롬프트 지시 vs 워크플로우 구조

"검증 지시를 빼라"를 **구조까지 빼라**로 오독하면 안 된다:

| 층위 | 예 | 신세대에서 |
|---|---|---|
| 프롬프트 지시 | "답하기 전에 다시 확인해라" (같은 컨텍스트 안) | **제거 후보** — 모델의 자체 검증과 중복 |
| 워크플로우 구조 | 별도 컨텍스트의 verifier 에이전트, writer-verifier 분리, 게이트 | **유지** — 신모델 가이드도 fresh-context verifier가 self-critique보다 낫다고 명시 |

같은 컨텍스트 안에서 "다시 봐라"는 편향을 공유한 재검토라 이득이 작지만, 깨끗한 컨텍스트의 독립 검증자는 작성자의 가정을 물려받지 않는다. 전자는 프롬프트 문제, 후자는 아키텍처 자산이다.

## 실무 체크리스트

기존 프롬프트/에이전트 정의를 신모델로 옮길 때:

1. "double-check / 다시 확인 / 검증 단계 추가" 류 지시 → 제거하고 A/B
2. "MUST / CRITICAL / 반드시" 강조 → 평서형으로 완화
3. 보고 필터("중요한 것만") → "전부 보고 + 하류 필터"로 역전
4. 단계별 미시 절차(step-by-step reasoning scaffold) → 목표·제약 서술로 대체 후 A/B
5. **남길 것**: 권한 경계·중단 조건·판정 규칙(어느 세대든 하네스 불변식), 독립 컨텍스트 검증 구조
6. 응답 길이·내레이션 스타일은 모델이 알아서 해주지 않는 축 — 원하는 케이던스를 **명시적으로 서술** (effort/thinking 설정은 사고량 제어지 출력 길이 제어가 아님)
