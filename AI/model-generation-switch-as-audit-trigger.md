# 모델 세대 교체는 에이전트 설정 점검 트리거로 쓰기 좋다

스킬 22개, 서브에이전트 14개를 굴리고 있다. 새 모델 세대로 넘어가면서 "짜는 방식이 많이 달라졌다"는 말을 듣고 전수 점검을 했다.

결론부터: 세대 차이 때문에 고친 건 예상보다 적었고, **세대와 무관하게 시간이 만든 드리프트가 훨씬 많았다.** 그런데 그건 평소엔 점검할 계기가 없다. 모델 교체가 그 계기가 되어준다.

찾은 것을 세 축으로 나눠 남긴다.

## 축 1 — 새 세대에서 새로 생긴 것

이게 제일 실속 있었다. 프레임워크가 진화하면 **본문 프롬프트로 하던 일이 설정 필드로 내려온다.** 만들 때 없던 필드라 알아서 찾아보지 않으면 계속 옛날 방식으로 쓴다.

| 전 (본문에 서술) | 후 (설정 필드) |
|---|---|
| "이 에이전트는 read-only, 코드를 수정하지 않는다" ×3회 선언 | `disallowedTools: Edit` |
| "이 스킬은 다른 스킬이 호출한다. 직접 부르지 마라" | `user-invocable: false` |
| "이 작업은 사용자가 명시적으로 요청할 때만" | `disable-model-invocation: true` |
| "깊이 생각해서 판단하라" | `effort: high` |

차이가 크다. 본문의 "하지 마라"는 지킬 수도 있고 안 지킬 수도 있지만, **도구를 안 주면 못 한다.** 실제로 "read-only"를 세 번 선언한 에이전트가 전체 도구를 열어두고 있었다.

진단 도구가 새로 생겼는지도 같이 본다. 어떤 스킬이 실제로 안 쓰이고 컨텍스트만 먹는지 보여주는 커맨드가 추가돼 있었다.

## 축 2 — 세대 차이로 무의미해진 것

여기가 "달라졌다"고들 하는 부분인데, 정작 고칠 게 많지 않았다.

- **강조어**: `MUST` / `NEVER` / `반드시`를 파일별 밀도로 뽑아보니 상위 3개 파일에 몰려 있고 나머지는 이미 평서형이었다. 신세대는 지시를 문자 그대로 따르므로 강조가 과잉 트리거를 만든다. (별도 정리: [신세대 LLM 프롬프팅](./prompting-newer-llms-remove-not-add.md))
- **의례적 확인 게이트**: "스캐폴딩 파일 목록입니다. 진행할까요?"처럼 선택지가 없는데 묻는 자리 8곳. 신세대는 요청받은 작업 도중에 허가를 더 자주 구하는 경향이 있어서, 이런 게 남아 있으면 증폭된다. 진짜 멈춰야 할 곳(외부로 나가거나 되돌리기 어려운 행동)만 남겼다.
- **모델 별칭 재배정**: 별칭이 가리키는 세대는 이미 올라가 있었다. 파일을 안 고쳐도 세대는 바뀐다. 대신 **부하와 배정이 뒤집혀 있는 것**을 찾았다. 판단 부하가 가장 큰 검증자가 가장 작은 모델에 배정돼 있었고, grep 기반 기계 검사가 가장 큰 모델을 쓰고 있었다. 서로 바꿨다.

## 축 3 — 세대와 무관한 드리프트

양으로는 이쪽이 압도적이었다. 컴파일러도 테스트도 없는 파일들이라 조용히 갈라진다.

**설정과 본문의 불일치.** 본문이 "리포트를 파일로 저장하라"인데 도구 목록에 `Write`가 없었다. 그 단계는 구조적으로 실행 불가였고 한참 아무도 몰랐다. 본문만 읽으면 안 보이고 설정과 대조해야 나온다.

**정본과 갈라진 복제본.** 프로젝트 규칙 문서의 내용을 편의상 에이전트 세 곳에 복사해 뒀는데, 문서가 나중에 개정되며 반대 내용이 됐다. 결과는 리뷰어가 정답을 오답으로 판정하는 것. 게이트 로그에 "이 규칙 오탐" 기록은 남아 있었지만 증상만 알려지고 근원은 그대로였다.

**사례 서사의 축적.** "○○ 작업 때 이런 일이 있어서 이렇게 한다" 문단이 50곳. 하나씩 넣을 땐 합리적이다. 근거를 남기고 싶으니까. 쌓이면 규칙이 사연에 묻힌다. 지시는 한 문장으로 남기고 근거는 회고 문서로 옮겼다.

**상주 컨텍스트 비대.** 스킬·에이전트의 `description`은 본문과 달리 **매 세션 전부 로드된다.** 어떤 걸 호출할지 판단해야 하니까. 36개 합계가 33k자(≈8k 토큰)였다. 본문을 아무리 잘 쪼개도 여기가 길면 매 대화가 그 비용으로 시작한다.

**반쯤 폐기된 컴포넌트.** 스킬 하나를 다른 쪽에 흡수하기로 하고 "흡수 중"이라 적어뒀는데 삭제는 안 하고 참조 다섯 곳이 남아 있었다. 두 스킬이 같은 상태 스키마를 각자 들고 드리프트. 폐기는 선언이 아니라 삭제로 해야 한다.

## 점검은 기계 검사로 좁힌다

36개를 다 읽을 순 없다. 후보를 먼저 좁혔다.

| 검사 | 방법 |
|---|---|
| 강조어 밀도 | `MUST\|NEVER\|반드시\|절대`를 파일별 줄 수로 나눠 정렬 |
| 설정↔본문 | 본문의 "저장하라 / 수정 금지"와 도구 목록 대조 |
| 깨진 참조 | 언급된 에이전트·스킬·경로·도구명이 실재하는지 |
| description 총량 | 전 파일 frontmatter의 description 글자수 합 |
| 중복 규칙 | 같은 문장이 2개 이상 파일에 있는지 |

읽는 건 여기서 걸린 것만.

## 정리

설정 파일에는 린터가 없어서 깨져도 아무도 안 알려준다. 그렇다고 "정기 점검"을 캘린더에 넣어봐야 안 하게 된다. **모델 세대 교체처럼 어차피 뭔가 확인해야 하는 시점을 트리거로 쓰는 편**이 현실적이다. 막상 열어보면 세대 얘기는 일부고 나머지가 본론이다.

축 1의 "본문의 하지 마라 vs 도구를 안 주면 못 한다"는 프롬프트 밖에서도 같은 모양으로 나타난다. 판정 축에서의 같은 원리: [시안 정합은 금지가 아니라 데이터로](./design-parity-needs-data-not-prohibition.md)
