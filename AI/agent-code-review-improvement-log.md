# 에이전트 코드 리뷰 개선 기록

에이전트 하네스(화면 개발 스킬 + 서브에이전트 리뷰어 2명)의 리뷰를 다듬었다. 출발점은 Claude Code 팀의 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)다. 요지는 두 가지다. 사람의 리뷰 시간을 줄이되 되돌림 비율이 오르지 않게 할 것, 그리고 리뷰가 회차를 거듭하며 **수렴**하게 만들 것. 이 글에서는 평균 리뷰 횟수가 2.08회에서 1.32회로 줄었다. 단계마다 던진 질문이 달라서 그 순서대로 정리한다.

## 1. 「이미 있는 건 뭔가」 — 대조부터

글의 장치를 우리 하네스와 한 줄씩 맞대 봤다.

| 이미 있음 | 없음 |
|---|---|
| 2회차부터 변경분만 재리뷰 · 회차 상한 · 반복 지적 표시 | 지적 출처 구분 · 유형 단위 묶기 · 지적별 처분 기록 · `REVIEW.md` · 리뷰 강제 |

있는 걸 다시 만들지 않으려면 이 표가 먼저다.

## 2. 「같은 지적이 왜 계속 돌아오나」 — 출력 형식

글에 따르면 반복 지적의 59%는 첫 회차부터 있던 코드였다. 회차마다 옛 버그를 몇 개씩 더 꺼낸 것이다. 그래서 리뷰어 출력을 이렇게 바꿨다.

- 지적마다 id와 출처(`introduced` / `pre-existing`)를 단다
- 원인 하나에 지적 하나만 쓴다. 쓰기 전에 스코프 전체를 검색해서 모든 위치를 그 지적 아래 나열한다
- 오케스트레이터가 지적마다 처분(고침 · 오판 · 의도 · 보류 · 반복)을 기록한다. 리뷰어 잡음을 재는 재료가 된다
- 3회차에도 blocker가 남으면 4회차는 패치가 아니라 접근 재검토부터 한다

## 3. 「무엇을 적을까」 — 지난 보고서로 정했다

`REVIEW.md`에 넣을 내용은 감으로 쓰지 않았다. 지난 리뷰 보고서 약 300건을 서브에이전트로 집계했다.

| 관찰 | 수치 |
|---|---|
| 3회차 이상 간 리뷰 범위 | 68개 중 30개 |
| 이월로 다시 실린 지적 중 info | 166건 중 125건 |
| 생성 코드를 겨냥한 지적 | 0건 |

blocker는 12개 유형에 몰려 있었다(실패를 화면에 안 띄움, 409 뒤 낡은 값, 저장 중 재진입, 포커스 유실 등). 이 유형들은 그대로 점검 순서가 됐다. 잡음 쪽 집계로는 규칙 두 줄을 만들었다. "확인 안 한 주장은 warning까지만", "기록된 결정은 지적 아님(blocker 제외)". 생성 코드 지적은 0건이라 건너뛸 경로로 적을 필요가 없었다.

## 4. 「어디에 둘까」 — 종류가 아니라 실리는 시점으로

처음엔 리뷰 스킬 폴더에 뒀다. 그런데 실제로 읽는 쪽은 리뷰어 에이전트였고, 스킬을 거치지 않고 리뷰어를 직접 부르는 경로도 있었다. `docs/`로 옮기면 에이전트가 "읽어라"는 지시를 기억해야 한다. 그래서 **언제 컨텍스트에 실리는가**로 나눴다.

| 둔 곳 | 실리는 시점 | 내용 |
|---|---|---|
| `.claude/rules/*.md` + `paths:` | 그 경로 파일을 열 때 | 결함 12유형 — 구현자와 리뷰어가 같이 받음 |
| 에이전트 `skills:` 미리 로드 | 리뷰어 시작 때 | 근거·범위·처분 절차 |

결함 목록을 경로 규칙으로 둔 이유가 있다. 회차를 늘린 건 구현 단계에서 생긴 결함이었다. 그러니 구현하는 쪽이 먼저 받는 게 리뷰에서 잡는 것보다 싸다. `REVIEW.md`라는 이름은 쓰지 않았다. GitHub용 Code Review 서비스가 루트에서 읽는 파일이고, 로컬 `/code-review`는 읽지 않는다.

## 5. 「정말 실리나」 — 카나리로 확인

경로 규칙이 **서브에이전트에도** 실리는지는 문서에 없었다. 규칙 파일에 "이걸 보면 답에 `CANARY-7F3K`를 넣어라"를 적었다. 지금 세션은 규칙 파일보다 먼저 떠서 새 파일을 인식할지 알 수 없었다. 그래서 새 headless 세션으로 돌렸다.

| 경우 | 결과 |
|---|---|
| 메인이 그 경로 파일을 읽음 | 실림 |
| 서브에이전트가 그 경로 파일을 읽음 | 실림 |
| 서브에이전트가 경로 밖 파일만 읽음 | 안 실림 |

**함정 하나.** `claude -p --allowedTools Read "프롬프트"`는 가변 인자 플래그가 프롬프트까지 먹는다. `--allowedTools=Read`로 쓰거나 프롬프트를 stdin으로 넘긴다.

## 6. 「리뷰를 안 돌리면?」 — 승인을 코드 지문에 묶기

리뷰 게이트는 스킬 지시문이었다. 그래서 바로 고친 것이나 리뷰 뒤 정리 수정은 리뷰 없이 올라갈 수 있었다. 글의 "승인은 특정 커밋에만 유효"를 push 훅으로 옮겼다.

- 리뷰어는 리뷰한 코드의 트리 해시(생성 코드 제외)를 보고서에 적는다
- 훅은 push할 HEAD의 해시와 비교한다. 두 리뷰어 모두 blocker 0이고 해시가 같을 때만 통과한다
- 리뷰 뒤 한 줄이라도 고치면 해시가 달라져 막힌다

## 7. 「막혀야 할 때 막히나」 — 시험이 전부 통과였다

임시 브랜치와 가짜 보고서로 시험했다. 도장 없음, 낡은 도장, blocker 1까지 **전부 통과**했다. 원인은 push 감지 정규식이었다. `git` 앞에 공백만 허용해서 `/usr/bin/git push`를 push로 보지 못했다. 이 정규식은 기존의 "문서 동반 가드"에서 복사한 것이었고, **그 가드도 그동안 한 번도 돈 적이 없었다.**

## 하지 않은 것

- **리뷰어에게 이전 지적 넘기기** — 글은 이렇게 반복을 막는다. 하지만 리뷰어가 검증할 수 없는 전제를 프롬프트에 넣으면 게이트가 지워진다. 그래서 반복 걸러내기는 오케스트레이터가 맡는다.
- **우회 플래그** — `SKIP_X=1`은 모델이 스스로 붙일 수 있다. 우회는 사람이 직접 push하는 경로만 남겼다.
- **CI 리뷰 단계** — 로컬 훅은 터미널 push를 못 막는다. 비용과 키 관리 문제로 다음 단계로 미뤘다.

## 정리

- 질문 순서: **이미 있는 건 → 왜 반복되나 → 무엇을 적나 → 어디에 두나 → 정말 실리나 → 안 돌리면 → 막혀야 할 때 막히나.**
- 리뷰 지침은 종류가 아니라 **실리는 시점**으로 나눈다. 구현자도 받아야 하는 건 경로 규칙으로 둔다.
- 문서에 없는 로딩 동작은 대조군을 둔 카나리로 확인한다.
- 지시문으로 거는 게이트는 우회된다. 승인을 코드 지문에 묶으면 리뷰 뒤 수정까지 잡힌다.
- 차단 훅은 **막히는 경우부터** 시험한다. 조용히 통과하는 가드는 있다고 믿게 만들어서 없는 것보다 나쁘다.
- 효과는 아직 재지 않았다. 처분 기록이 쌓이면 위 기준선(68개 중 30개)과 비교한다.
