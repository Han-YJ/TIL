# 인앱 도움말 의도 판정 — 임베딩에서 선택형 LLM, 그리고 규칙 후처리까지

업무용 웹앱에 「물어보면 해당 화면으로 이동하고 버튼을 강조해 주는」 도움말을 붙일 수 있는지 하루 동안 실측했다. 핵심은 사용자 문장을 **미리 정의한 intent id 중 하나로 고르는 것**이다. LLM 이 답변이나 셀렉터를 직접 만들게 하지 않고, id 를 고르면 그 id 에 묶인 화면 경로·강조 대상·안내문을 코드가 꺼낸다(레지스트리 방식). 그래서 정확도는 「id 를 맞게 골랐나」로 바로 잴 수 있다.

**측정 방법**: intent 53개, 발화 228개로 정답 셋을 만들었다. intent 종류는 화면 이동(navigate), 단계 안내(guide), 단답(answer), 「그 기능은 없다」 안내(limit) 네 가지다. 이후 회차마다 **규칙을 고정한 다음에 새 셋(holdout)을 열었다.** 셋을 먼저 보고 규칙을 고치면 수치가 부풀기 때문이다.

## 과정

### 1. 임베딩 kNN

- **시도**: `multilingual-e5-small` 로 발화를 임베딩하고 최근접 이웃으로 intent 를 골랐다
- **결과**: 정답률 **18~22%**
- **원인**: 같은 화면 안의 동작(비활성화·삭제·권한 변경·팀 변경)은 쓰는 단어가 거의 같다. 임베딩은 문장이 비슷하다는 건 잡지만 「무엇을 하려는가」는 못 가른다
- **해결**: 임베딩 방식은 기각하고 선택형 LLM 으로 바꿨다

### 2. 선택형 LLM

- **시도**: 후보 id 목록과 각 설명을 주고 하나를 고르게 하는 분류 API(Jev: 선택 choice, 점수 score, 예/아니오 판정 noul)를 썼다
- **결과**: 1단계 정답률 **91%**. 확신도 0.9 이상인 문장(전체의 68%)은 **전부 정답**이었다
- **설계**: 「0.9 이상이면 바로 실행, 그 아래면 상위 3개로 되묻기」로 정했다. 비용은 실험 전체를 합쳐 약 $0.54 였다. 실제 결정 요인은 비용이 아니라 데이터 계약이다(사용자 문장이 외부로 나가므로 보관 정책과 처리 지역 확인)

### 3. 한 화면으로 시범 (v1)

- **시도**: 사용자 관리 화면 하나를 골랐다. 기획 문서에서 「할 수 있는 것(guide)」과 「할 수 없는 것(limit)」을 뽑아 레지스트리를 만들고, 정답을 모르는 상태로 받은 발화로 쟀다
- **결과**: **84%**. 상위 3개 안에는 100% 들어 있었다
- **원인**: 오답을 읽어 보니 두 종류였다. 기획 문서에 없는 「할 수 없는 것」이 빠져 있었고, 권한이 낮은 사람이 관리자 기능을 묻는 경우를 LLM 이 그 기능 안내로 보냈다

### 4. 권한 규칙 + 빠진 limit (v2)

- **해결**: 빠진 limit 7건을 추가했다. 그리고 **권한 규칙 후처리**를 넣었다. 묻는 사람 권한으로 할 수 없는 기능이면 「권한 없음」 안내로 바꾼다. 권한은 LLM 이 추측할 일이 아니라 코드가 아는 사실이라서다
- **결과**: 새 셋 **88%**
- **남은 원인**: 비슷한 intent 끼리 설명문이 겹쳐 LLM 이 헷갈렸다

### 5. 설명문 정비 (v3)

- **해결**: intent 설명문을 서로 겹치지 않게 다시 썼다
- **결과**: 새 셋 **97%**
- **의심**: 셋이 쉬웠던 건 아닌지 확인할 필요가 있었다

### 6. 어려운 셋으로 재측정 (v4)

- **시도**: 일부러 애매한 문장을 모은 셋을 받았다
- **결과**: **70~78%** 로 떨어졌다
- **원인**: 「권한이 뭐야」 같은 **개념 질문**을 「권한 바꾸는 법」으로 보냈다
- **해결**: 「방법을 묻나, 개념을 묻나」를 예/아니오 판정으로 따로 물었다

### 7. 판정 순서 + 지원 범위 + 옆 도메인 (v5)

- **원인 1**: 개념 판정보다 권한 규칙이 먼저 적용돼서, 개념 질문이 「권한 없음」으로 덮였다
  - **해결**: 개념 판정을 맨 앞으로 옮겼다
- **원인 2**: 「여러 명 한꺼번에」·「다음 달 1일에 자동으로」처럼 앱이 지원하지 않는 요청을 단건 안내로 보냈다
  - **해결**: 예/아니오 판정 하나를 더 두고, 걸리면 「지원 안 함」으로 답한다
- **원인 3**: 거래처 담당자 이야기를 사용자 관리로 보냈다. 고를 수 있는 후보에 거래처 쪽 intent 가 아예 없었다
  - **해결**: 거래처 관리 intent 를 레지스트리에 추가했다
- **결과**: 어려운 셋 **66 → 79%**

### 8. 막힌 원인 찾기 → 회사명 대조 (v6)

- **가설**: 같은 화면 intent 점수를 합산하느냐 최댓값으로 고르느냐가 오답을 만든다
  - **검증**: 오답을 두 방식으로 다시 계산했더니 차이가 0이었다 → **기각**
- **실제 원인**: 오답을 하나씩 읽어 보니 **직원 계정과 외부 거래처 담당자를 혼동**하고 있었다. 「○○스틸 김과장 연락처 바꿔줘」를 사용자 관리로 보낸 식이다
- **기각한 해결**: 이름 대조(문장 속 사람이 직원 목록에 있나)는 상한이 81% 였다. 게다가 정답 사람 목록이 있어야 해서 실제로는 구현할 수 없다
- **해결**: 정답 라벨 없이 판정하는 **회사명 대조** 규칙을 넣었다. 문장에 아래 셋 중 하나가 있으면 사용자 관리 후보를 빼고 다시 고른다
  - 거래처 회사명
  - 「~스틸·~제강·~건설」 같은 회사 이름 꼴
  - 「거래처·업체·실무자」 같은 말
- **결과**: 어려운 셋 **79 → 85%**. 기존 228문장에서 새로 틀린 문장은 0건이었다. 새로 받은 사람 언급 위주 셋에서는 **94%** 였다
- **실수**: 문맥어에 「구매팀」을 넣었는데, 이건 앱이 기본으로 만드는 **사내 팀 이름**이었다. 그래서 직원 문장 3건이 거래처로 넘어갔다. 이 단어를 빼면 새로 틀린 문장이 0건이 된다. 문맥어는 테넌트 데이터(팀 이름 등)와 겹치지 않는지 대조해야 한다

## 최종 구성

1. LLM 을 한 번 호출한다. intent 선택, 개념 질문 여부, 지원 범위 밖 요청 여부를 함께 묻는다
2. 회사명 대조로 거래처 맥락이면 사용자 관리 후보를 뺀다
3. 개념 질문이면 개념 설명으로 답한다
4. 묻는 사람의 권한으로 규칙을 적용한다
5. 일괄·예약 요청이면 「지원 안 함」으로 답한다
6. 확신도가 0.9 이상이면 바로 실행한다. 그 아래면 상위 3개로 되묻고, 판정할 수 없으면 범용 LLM 으로 넘긴다

## 배운 것

- 같은 화면 안의 동작을 가르는 의도 분류에서 작은 임베딩 kNN 은 쓸 수 없다(18~22%). 후보 설명을 주고 고르게 하는 LLM 이 압도적이다(91%)
- LLM 이 잘하는 것(어떤 동작인가)은 LLM 에 맡긴다. 코드가 확실히 아는 것(권한, 지원 범위, 거래처 맥락)은 규칙 후처리로 덮는다. 이때 **규칙 적용 순서**도 정확도에 영향을 준다
- 확신도 임계값을 정해 두면 「바로 실행」 구간을 오답 없이 확보할 수 있다. 나머지는 되묻기로 처리한다
- 정답률이 막히면 집계 방식부터 의심하기 전에 **오답 문장을 직접 읽어라.** 원인은 대개 도메인 혼동이고, 정답 라벨 없이 판정할 수 있는 규칙 하나로 풀린다
- 규칙은 새 셋을 열기 전에 고정한다. 셋을 보고 고친 값은 참고치로만 둔다
