# 에이전트 하네스는 기억이 아니라 트랜스크립트로 고친다

스킬 21개, 서브에이전트 14개를 굴린다. 그동안 이것들을 고치는 방식은 **회고**였다 — 한 회차가 끝나면 "뭐가 불편했지"를 떠올려 정의를 손봤다. 이번엔 다르게 해봤다. 로컬에 쌓인 대화 트랜스크립트를 집계해서 **결함을 숫자로 먼저 찾고** 고쳤다.

결론부터: 회고로는 못 찾았을 것들이 나왔고, 반대로 **회고가 만든 내 확신 두 개가 측정으로 깨졌다.**

## 측정에서 두 번 틀렸다 — 이게 제일 실속 있는 교훈

트랜스크립트 집계는 쉬워 보이는데 두 군데서 조용히 틀린다. 둘 다 **에러 없이 그럴듯한 숫자**를 내서 더 위험하다.

**① 서브에이전트 로그는 한 단계 더 깊다**

메인 세션은 `<프로젝트>/<세션UUID>.jsonl` 인데, 서브에이전트는 `<프로젝트>/<세션UUID>/subagents/agent-*.jsonl` 에 따로 쌓인다. `*/*.jsonl` 글롭은 이걸 통째로 놓친다. 나는 이걸 놓치고 **"서브에이전트 로그가 아예 없다"고 결론까지 냈다.** 재귀 탐색으로 바꾸니 전체 비용의 14%가 거기 있었다.

**② 같은 `message.id` 가 한 파일 안에서도 반복 기록된다**

스트리밍·재개 때문인지 동일 메시지가 여러 줄로 남는다. 실측하니 raw 28,279건 → 고유 7,166건, **약 4배**였다. 파일 단위로만 중복을 거르면 2.3배 뻥튀기된 숫자가 나온다. 실제로 두 집계가 2.3배 차이 나는 값을 내놓고 서로 안 맞아서야 알아챘다.

> 집계 규칙 두 줄: **재귀 탐색**, **전역 `message.id` dedupe**. 그리고 두 가지 방법으로 독립 집계해서 값이 일치하는지 본다 — 안 맞으면 하나는 틀린 거다.

## 비용은 단가가 아니라 "턴당 프리픽스"에 붙는다

흔한 통념은 "출력 토큰이 입력의 5배라 비싸다"인데, 에이전트 워크로드에선 반대였다.

| | 비중 |
|---|---|
| 입력 토큰 | 99.8% |
| 출력 토큰 | 0.2% |
| **입력이 차지한 비용** | **92%** |

입력:출력 토큰비가 **554:1** 이었다. 매 턴 대화 전체를 다시 보내니, 컨텍스트가 커질수록 **질문 크기와 무관한 고정비**가 붙는다. 같은 질문이 컨텍스트 100k 일 때와 800k 일 때 **4배** 차이가 났다.

그래서 유효한 레버는 출력을 줄이는 게 아니었다:

1. **작업 단위가 바뀌면 세션을 끊는다** — 비용의 77%가 컨텍스트 400k 초과 구간에서 났다. 세션 평균 547턴인데 400k 돌파는 중앙값 149턴, 즉 뒤쪽 3/4을 비싼 구간에서 보낸다
2. **툴 결과를 좁힌다** — 한 번 들어온 툴 결과는 그 세션 **남은 모든 턴에서 재과금**된다. 100턴 남은 시점에 큰 파일을 통째로 읽는 건 그 크기 × 100 을 지불하는 것
3. **읽기가 많은 작업은 서브에이전트로 격리** — 실측 3.4배 저렴했다. 결론만 돌아오고 탐색 과정이 메인 프리픽스에 안 남는다

반대로 **손대봐야 소용없는 것**도 숫자로 갈렸다: 출력·사고 토큰(2.3%), 시스템 프롬프트 다이어트(1만 토큰당 1.7%), 모델 다운그레이드(턴이 늘면 오히려 손해).

## 점진 공개 — "분기를 만드는 것"이 아니다

스킬 본문은 활성화 시점에 **통째로** 컨텍스트에 들어온다. 그래서 큰 스킬은 안 쓰는 절차까지 매 턴 값을 치른다.

해법은 조건부 절차를 별도 파일로 내리고 원래 자리에 **트리거 문장만** 남기는 것이다. 참조 파일은 실제로 읽기 전까지 0 토큰이다.

```markdown
### <원래 제목 유지>

<조건>일 때만 필요하다. 그때 `references/<파일>.md` 를 읽고 그 기준대로 처리한다 —
SSoT 는 그 파일이며 여기 요약본을 두지 않는다.
```

여기서 자주 오해하는 것: **새 분기를 만드는 게 아니다.** 조건은 원래 문장 안에 이미 있었고, 바뀌는 건 "읽고 안 쓴다" → "안 읽는다" 뿐이다. 프론트엔드의 `dynamic import()` 와 같다 — 라우팅은 원래 있었고 청크를 언제 받느냐만 바뀐다.

세 스킬에 적용해 항상 로드되는 본문을 **26~27%** 줄였다. 두 가지 규칙이 붙는다:

- **요약본을 남기지 않는다** — 남기면 원본과 어긋나고, 모델은 요약을 믿는다
- **트리거 문장이 전부다** — 모호하면 영영 안 읽혀 규칙이 증발하고, 느슨하면 매번 읽혀 이득이 0이 된다. 판단이 실제로 일어나는 자리에 `"~할 때만"` 으로 조건을 박는다

그리고 **전부가 분할 대상은 아니다.** 한 스킬은 큰 절이 둘 다 "기본 동작"이라 분할하면 포인터 오버헤드만 늘어 그대로 뒀다. always-path 는 내려봐야 이득이 없다.

## 규칙은 강제되는 층에 둬라

이번에 제일 크게 배운 것. 같은 "규칙"이라도 층이 다르다.

| 층 | 예 | 강제되나 |
|---|---|---|
| 스키마·설정 필드 | 에이전트의 도구 화이트리스트, 모델 지정 | **예** — 어기면 동작 자체가 막힘 |
| 훅 | 커밋·푸시 전 검사 | **예** — 결정적으로 차단 |
| 본문 산문 | "이럴 땐 이렇게 해라" | **아니오** — 모델이 안 읽으면 그만 |

실증이 있었다. 문서에 "새 컴포넌트는 이 워크플로를 타라"고 적어뒀는데, 한 달간 관련 커밋 121개가 그 체인을 **통째로 우회**했다. 산문이라 아무도 안 막았다.

그래서 점진 공개를 넣은 뒤 **참조 파일이 실재하는지 검사하는 push 훅**을 같이 넣었다. 점진 공개 자체가 산문 트리거라 강제되지 않는 층에 있었기 때문이다. 다만 훅이 덮는 건 "파일이 있는가"까지고, **"조건이 맞을 때 실제로 읽는가"는 여전히 산문**이다. 거기까진 기계로 못 잡는다.

## 측정도 틀린다 — 반문이 두 번 맞았다

측정 기반이라고 무오류가 되진 않았다. 이번에 내 진단이 두 번 뒤집혔다.

- **"서브에이전트 로그가 없다"** → 있었다. 글롭이 얕았다. 지적받고 다시 봤다
- **"한 검증기가 한 화면을 15라운드나 돌았다"** → 세 개의 독립 실행 × 각 5라운드였다. 세션 단위로만 세서 그렇게 보였다
- **"매 라운드 잘못 고쳤나 보다"** → 아니었다. 절반은 정상 확인이었고, 반복의 진짜 원인은 **고칠 수 없는 항목을 라운드마다 재발견**하는 것과 **라운드마다 검증 범위가 흔들리는 것** 두 개였다

세 번 다 "이상하다"는 반문에서 시작됐다. 숫자를 들고 있어도 **그 숫자가 무엇을 센 것인지**는 따로 검증해야 한다. 특히 집계 단위(세션 vs 실행 vs 파일)를 잘못 잡으면 숫자는 맞는데 결론이 틀린다.

## 정리

- 하네스는 회고 말고 **트랜스크립트 집계**로 고친다. 기억은 드리프트하고 로그는 안 한다
- 집계는 **재귀 탐색 + 전역 dedupe**, 그리고 독립 두 경로 교차검증
- 에이전트 비용은 **턴당 프리픽스**에 붙는다. 세션 길이와 툴 결과 크기가 레버고, 출력은 아니다
- 스킬은 조건부 절차를 참조 파일로 내린다. 단 **always-path 는 놔둔다**
- 지켜야 하는 규칙은 산문이 아니라 **스키마·훅**에 넣는다
