# 800행 그룹 테이블 — 재고 memo 하고, 다시 재고 가상화했다

단계별 그룹 아코디언 목록(그룹당 100건 × 단계 수, 행마다 별 토글·드로어 아이콘·선택적 하단 패널)이 느리다는 감각만 있고 숫자는 없던 상태에서 출발했다. TanStack Table 기반 공용 DataTable 을 고쳐야 했고, 같은 컴포넌트를 쓰는 화면이 25곳이라 "일단 가상화"는 비싼 선택이었다. 순서는 **측정 → memo → 재측정 → 가상화 → 재측정**.

## 1. 측정 방법 — dev 숫자는 버린다

- `next build --profile` 로 **프로덕션 + 프로파일링 빌드**를 띄운다. dev 빌드는 StrictMode 이중 렌더·개발용 검사 때문에 비율조차 믿을 수 없다.
- 목록 섹션을 임시 `<Profiler onRender>` 로 감싸 commit 마다 `actualDuration` 을 `window` 배열에 쌓는다. 측정이 끝나면 되돌리고 커밋하지 않는다.
- Playwright 로 진입 → 별 토글 → 정렬 → 그룹별 「더 보기」 를 누르고, 동작 전 배열을 비운 뒤 1.2초 뒤 수집한다.
  - `PerformanceObserver({ type: 'longtask' })` 합계 = 사용자가 체감하는 "멈춤"
  - `document.getElementsByTagName('*').length` = DOM 노드 수
- CDP `Emulation.setCPUThrottlingRate(4)` 로 4배 감속을 한 번 더 — 개발 머신이 빠르면 "괜찮아 보이는" 숫자가 나온다.
- 시드는 소모용 태그를 붙여 API 로 넣고, 측정이 끝나면 지운다. 공유 테스트 테넌트에 800건을 남겨 두면 다른 e2e 를 오염시킨다.

일반 조건 3회, 감속 2회. 회차 간 편차가 5% 안이라 평균을 썼다.

## 2. 첫 숫자 — 비용이 행 수에 비례한다

| 동작 | commit 합 | long task 합 | 4배 감속 long task |
|---|---|---|---|
| 첫 화면 (301행) | 87ms | 88ms | 908ms |
| 별 토글 1회 (301행, commit 7번) | 147ms | 248ms | 908ms |
| 정렬 (301행, commit 11번) | 234ms | 452ms | 1,724ms |
| 「더 보기」 (778→844행) | 391ms | 694ms | 3,011ms |
| 별 토글 1회 (844행) | 288ms | 509ms | 2,156ms |

DOM 은 301행에 13,332개, 844행에 36,634개(행당 ~44). 별 하나에 commit 이 7번 돌고 매번 표 전체가 다시 그려지고 있었다.

## 3. memo — TanStack Table 에서 `React.memo` 기본 비교는 무력하다

행 컴포넌트를 `memo` 로 감싸는 것만으로는 아무것도 안 줄어든다.

- **`Row` 객체는 data 가 바뀔 때마다 전부 새로 만들어진다.** 별 하나를 뒤집으면 낙관 갱신이 새 그룹 배열을 만들고, 행 모델이 통째로 재계산된다. 바뀌지 않은 행도 `row` prop 이 새 참조다.
- 그래서 비교 기준을 **레코드 단위**로 바꿨다: `row.original` 참조 · `row.id` · `row.index` · 선택 여부(셀이 `row.getIsSelected()` 를 읽으므로 따로 prop 으로) · 컬럼 배열. 나머지 prop 은 얕은 비교.
  - TanStack Query 의 structural sharing 과 낙관 갱신의 `map(item => item.id === id ? {...item} : item)` 덕분에 안 바뀐 행은 `original` 이 같은 참조로 남는다.
- **소비처 인라인 핸들러** (`onRowClick={(row) => ...}`) 가 매 렌더 새 함수라 비교가 또 깨진다. 공용 컴포넌트 안에서 "참조는 고정, 호출은 최신"인 콜백으로 감싸 소비처 25곳을 고치지 않았다. 최신 함수 대입은 렌더가 아니라 `useLayoutEffect` 에서 한다 ([latest-ref 패턴은 React Compiler 시대에 깨진다](./latest-ref-pattern-breaks-under-react-compiler.md) 의 경고와 같은 축 — 이벤트 핸들러에서만 부르는 콜백이라 커밋 후 대입이 문제되지 않는다).
- **이 memo 는 계약을 바꾼다.** 이전엔 "셀은 부모와 함께 늘 다시 그려진다"가 공짜로 성립했다. memo 이후엔 셀이 `row` 와 컬럼만 읽어야 한다. 셀이 렌더 중 `ref.current` 로 외부 상태를 읽고 있었다면 이 순간 stale 버그가 된다 — 머지 전에 컬럼 정의 파일 전부에서 렌더 중 ref 읽기가 0건인지 확인했다. 계약은 공개 prop 의 JSDoc 에 적었다.

memo 후:

| 동작 | commit 합 | long task 합 | 4배 감속 long task |
|---|---|---|---|
| 별 토글 (844행) | 288 → **4ms** | 509 → **0ms** | 2,156 → 121ms |
| 「더 보기」 (→844행) | 391 → **20ms** | 694 → **0ms** | 3,011 → 194ms |
| 정렬 (301행) | 234 → 100ms | 452 → 205ms | 1,724 → 822ms |
| 첫 화면 (301행) | 87 → 90ms | 88 → 72ms | 908 → 893ms |

바뀐 행만 그리는 동작은 해결됐다. **정렬은 반만** — 정렬은 모든 행의 `index` 를 바꾸므로 전부 다시 그려야 한다. **첫 화면과 DOM 은 그대로** — 그려야 하는 행 수 자체가 원인이라 memo 대상이 아니다. 여기서 가상화가 "있으면 좋은 것"에서 "필요한 것"으로 바뀌었다. memo 를 먼저 하지 않았으면 이 구분을 숫자로 못 했다.

## 4. 그룹 테이블 가상화에서 걸린 것들

`@tanstack/react-virtual` 의 `useVirtualizer` 를 붙였다. 공식 "virtualized rows" 예제와 달랐던 지점:

- **가상화 대상은 `rows` 가 아니라 평탄화한 렌더 아이템이다.** 그룹 헤더 행·데이터 행·행 하단 패널·그룹별 「더 보기」 footer 가 한 목록에 섞여 있다. `getItemKey` 를 종류별로 유일하게(`panel:<id>`·`footer:<id>`) 만들어야 측정 캐시가 섞이지 않는다.
- **높이가 섞여 있으면 `measureElement` 가 필수다.** 데이터·그룹 행은 size 상수로 정확히 추정되지만 패널은 내용 따라 다르다. 패널 추정치는 지금까지 실측한 패널 높이의 평균으로 둬서 스크롤바 튐을 줄였다.
- **spacer 행 대신 rowgroup 패딩.** `role="rowgroup"` 안에 빈 `div` 를 넣으면 ARIA 필수 자식(row → cell) 규칙이 깨진다. 위아래 그리지 않은 높이는 rowgroup 의 `paddingTop/Bottom` 이 받는다. 스크롤 영역 안에 sticky 헤더가 있으면 그 높이를 `scrollMargin` 으로 넘기고 `start - scrollMargin` 으로 계산한다.
- **`:last-child` · `:nth-child(even)` 가 거짓말을 한다.** 일부만 그리면 DOM 형제 순서 ≠ 실제 순번이라 마지막 행 구분선·줄무늬가 스크롤 중 엉뚱한 행에 붙는다. 가상화 여부와 무관하게 아이템 순번으로 class 를 붙이도록 바꿨다(비가상화 결과는 동일).
- **포커스된 행이 스크롤로 언마운트되면 포커스가 `body` 로 떨어진다.** 비모달 드로어는 닫힐 때 열기 전 포커스 요소로 돌아가는데, 그 행이 사라져 있으면 갈 곳이 없다. 마지막으로 포커스가 든 아이템을 `rangeExtractor` 로 항상 범위에 넣고, 창에서 떨어진 그 한 행만 `position: absolute; top: start - scrollMargin` 으로 제자리에 둔다 — 연속 구간 + 패딩 레이아웃을 깨지 않는다.
- **로딩·빈 상태에 패딩을 걸지 말 것.** 데이터를 든 채 스켈레톤을 띄우면 그 아래 전체 행 높이(200행 ≈ 10,000px)만큼 빈 스크롤이 남는다. 리뷰에서 잡혔다.
- opt-in 이고, 표 안 스크롤(`fillHeight`)일 때만 켠다. 페이지 전체가 스크롤하는 표는 window 기준 가상화가 따로 필요하고, 순서 바꾸기(드래그) 표는 드롭 판정에 전 행이 필요해 끈다.

최종:

| 동작 | commit 합 원본 → memo → 가상화 | long task 합 | 4배 감속 long task |
|---|---|---|---|
| 첫 화면 (309행) | 87 → 90 → **17ms** | 88 → 72 → **17ms** | 908 → 893 → 476ms |
| 별 토글 (844행) | 288 → 4 → 3ms | 509 → 0 → 0ms | 2,156 → 121 → **0ms** |
| 정렬 (301행) | 234 → 100 → **15ms** | 452 → 205 → **0ms** | 1,724 → 822 → **72ms** |
| 「더 보기」 (→844행) | 391 → 20 → 12ms | 694 → 0 → 0ms | 3,011 → 194 → **0ms** |
| DOM (309 / 849행) | 13,332 / 36,634 → **1,339 / 1,395** | | |

첫 화면 감속 476ms 는 표(72ms) 밖 — hydration·필터 바 쪽이라 다음 과제다. 대가는 하나: 그리지 않은 행은 브라우저 찾기(Ctrl+F)에 안 걸린다.

## 5. 테스트에서 배운 것

- **jsdom 에서 가상 행은 0개다.** `@tanstack/virtual-core` 는 스크롤 요소 크기를 `offsetWidth/offsetHeight` 로, 행 실측을 `getBoundingClientRect` 로 읽는다. 둘 다 0 이면 창이 비어 아무것도 안 그린다. `role` 기준으로 둘 다 스파이해서 "스크롤 영역 400px · 행 52px" 를 흉내 냈다. 실제 스크롤은 Storybook play(900행 스토리에서 끝까지 스크롤 → 복귀 → 그룹 접기)로 덮었다.
- **"최신 핸들러로 간다" 테스트가 고정 콜백을 빼도 통과했다.** 핸들러가 렌더마다 바뀌는 값을 하나도 담지 않아서 옛 핸들러를 불러도 결과가 같았다. 토글 횟수를 핸들러 결과에 섞자 회귀를 잡았다. 새 단언마다 해당 코드를 일부러 빼고 실패하는지 확인했다 — memo 제거, 고정 콜백 갱신 제거, 포커스 유지 제거, 패딩 조건 제거 모두 해당 테스트만 빨개졌다.
- React Compiler lint: 훅이 ref 를 담은 객체를 돌려주면, 렌더 중 그 객체의 **다른 속성**을 읽어도 "Cannot access refs during render" 가 난다. 반환값을 처음에 구조 분해하면 풀린다.

## 요약

- 숫자 없이 가상화부터 넣었으면 "별 토글이 느린 이유"(전 행 재렌더)와 "첫 화면이 느린 이유"(DOM 양)를 구분하지 못했다. memo 를 먼저 하고 재니 둘이 갈렸다.
- TanStack Table 행 memo 는 `Row` 가 아니라 `row.original` 로 비교해야 하고, 그 순간 "셀은 row 만 읽는다"는 계약이 생긴다.
- 그룹·패널이 섞인 테이블의 가상화는 렌더 아이템 평탄화 + 실측 높이 + 패딩 + 순번 기반 class + 포커스 행 보존까지 가야 "그냥 일반 표처럼" 동작한다.
