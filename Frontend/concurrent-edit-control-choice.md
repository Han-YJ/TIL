# 동시 편집 충돌 제어는 "폼 길이 × 유실 비용"으로 고른다

같은 데이터를 두 사용자가 동시에 편집하는 상황을 다루는 방식은 크게 셋이고, 선택 기준은 **편집 세션의 길이**와 **충돌 시 잃는 작업의 비용**이다.

## 세 가지 방식

### ① 낙관적 충돌 감지 (optimistic concurrency)
- 락 없이 편집하게 두고, **저장 시점에** 버전(또는 updatedAt)을 비교한다. 그 사이 다른 저장이 있었으면 409로 거부하고 "다른 사용자가 수정했어요" 안내 후 최신 값으로 갱신.
- 서버는 버전 필드 비교만 하면 돼서 인프라가 거의 공짜. 대신 충돌 시 나중 저장자의 입력이 유실된다(재입력).
- **짧은 폼 · 충돌이 드문 CRUD SaaS의 기본값.**

### ② 비관적 락 (pessimistic lock)
- 편집 진입 시 서버에서 락을 획득하고, 점유 중이면 다른 사용자의 진입 자체를 차단한다("OO님이 편집 중입니다" 모달).
- 판정은 항상 서버가 원자적으로 — FE가 "락 걸렸나?" 조회 후 진입하는 방식은 그 틈에 둘 다 들어가는 레이스가 생긴다. 누르는 순간 획득을 시도하고 성공/실패 응답으로 갈라야 한다.
- 브라우저 강제 종료 같은 이탈로 해제가 보장되지 않으므로 **heartbeat(주기 ping) + 무활동 만료**가 세트로 필요하다. 이게 없으면 퇴근한 사용자가 락을 영원히 물고 있게 된다.
- 획득·해제·heartbeat 3종 API + 좀비 락 처리라는 운영 비용을 떠안는 대신 작업 유실이 0. **긴 문서/폼 편집이 정석 용례** — WordPress 글 편집(Heartbeat API), ERP 계열이 이 패턴.

### ③ 실시간 협업 병합 (OT/CRDT)
- 둘 다 편집하고 실시간 병합 — Google Docs·Figma·Notion. UX 최상, 구현 비용 최대. 일반 CRUD 앱에선 논외.

## 선택 기준

| 조건 | 선택 |
|---|---|
| 필드 몇 개짜리 짧은 폼, 충돌 확률 낮음, 재입력 비용 낮음 | ① 낙관적 |
| 수십 분 세션, 중간 저장/진행 상태가 서버에 쌓임, 충돌 시 병합 불가 | ② 비관적 락 |
| 동시 편집 자체가 핵심 가치 | ③ 실시간 병합 |

## 체감 포인트

스펙이 "편집 락"을 요구하더라도 대상 작업의 성격을 대조해볼 것 — 짧은 메타 폼에 락+heartbeat는 과한 경우가 많고, 반대로 필드별 승인/거부가 쌓이는 긴 검토 세션은 낙관적으로 수습이 안 된다. 한 제품 안에서도 화면마다 답이 다르다.
