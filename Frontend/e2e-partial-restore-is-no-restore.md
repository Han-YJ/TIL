# 공유 상태를 바꾸는 e2e는 되돌리기가 반쪽이면 안 고친 것과 같다

공유 테스트 환경(하나의 테넌트·계정·전역 설정)을 쓰는 e2e에서, 값을 바꾸고 **일부만** 되돌리는 코드를 만났다. 주석이 이렇게 말하고 있었다.

```
} finally {
  // B 플래그만 되돌린다.
  // A 플래그는 되돌리지 않는다: 유일한 A일 때 해제하면 0개가 돼 UI가 저장을 막는다.
}
```

논리는 맞다. UI로는 정말 그 상태에 도달할 수 없다. 그래서 되돌리지 않기로 한 것이고, 그 한 번의 실행으로 환경이 **영구히** 바뀌었다.

## 왜 몇 주 뒤에 드러나나

바꾼 값이 다른 파생값의 입력이면, 그 파생을 단언하는 **남의 스펙**이 빨개진다. 그 스펙 담당자는 자기 코드를 의심하며 시작한다. 커밋 시점과 증상 시점이 몇 주 떨어져 있어 원인 커밋을 역추적할 단서도 없다.

e2e가 CI 게이트가 아니면 이 간극이 더 벌어진다. 각자 자기 피처 스펙만 돌리니 오염된 스펙 자신은 계속 초록이고, 전수를 돌리는 사람이 나타날 때까지 아무도 모른다.

## 같은 계열의 다른 함정 — 백업을 기준으로 삼는 복원

```js
beforeAll(async () => { backup = await read(); });   // 현재 값을 떠 둔다
afterAll(async () => { await write(backup); });      // 그 값으로 되돌린다
```

정상 종료에서는 맞다. 하지만 `afterAll`이 **한 번이라도 안 돌면**(크래시·타임아웃·중단) 오염된 값이 남고, 다음 런의 `backup`이 그 오염값이 된다. 그때부터 복원할수록 오염이 굳는다.

## 대응

**복원이 아니라 리셋.** 현재 값을 떠서 되돌리지 말고, 알려진 기준값으로 맞추고 시작한다.

```js
beforeEach(async () => { await write(KNOWN_BASELINE); });
afterAll(async () => { await write(KNOWN_BASELINE); });
```

앞 런이 어떻게 끝났든 같은 자리에서 출발한다.

**UI로 못 돌리면 API로 돌린다.** "유일한 A를 해제할 수 없다"는 제약이 UI 폼의 검증일 뿐이라면, 시드가 쓰는 API 경로에는 그 제약이 없을 수 있다. 또는 원본을 건드리지 말고 **버릴 대상을 만들어** 거기에 플래그를 세우고 캡처 후 지운다.

**되돌릴 수 없는 변경이면 그 테스트를 다시 설계한다.** "되돌리지 않는다"는 주석은 해법이 아니라 부채 선언이다.

## 점검 목록

- 이 스펙이 바꾸는 것이 **이 스펙만의 것인가**, 다른 스펙도 읽는 공유값인가
- 복원이 예외·타임아웃·중단에서도 도는가
- 복원의 기준이 **고정값**인가, 그때그때 읽은 값인가
- 표시용 이름·라벨처럼 사소해 보이는 값도 포함했는가 — 정렬 순서나 기대 문자열을 단언하는 스펙이 그것을 읽는다
