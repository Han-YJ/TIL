# 업그레이드 후 실패가 늘었다는 숫자만으로는 회귀를 말할 수 없다

프레임워크를 올리고 e2e를 돌렸더니 실패가 10건에서 14건이 됐다. 업그레이드가 4건을 깨뜨린 것처럼 보이지만, **그 숫자만으로는 아무것도 증명되지 않는다.**

## 왜 문제가 되나

스위트에 만성 플레이크가 섞여 있으면 실패 건수는 런마다 달라진다. 같은 코드로 두 번 돌려도 10건과 14건이 나온다.

더 나쁜 건 **실패 집합이 매번 바뀐다**는 것이다. 이번 런에서 A·B가 빨갛고 다음 런에서 C·D가 빨갛다면, "업그레이드 후에만 나온 C·D"는 회귀처럼 보이지만 실은 원래 흔들리던 것이다. 반대로 진짜 회귀가 플레이크 뒤에 묻힐 수도 있다.

## 대응

**같은 커밋에서 이전 버전 기준선을 돌려 대조한다.**

```
git checkout --detach <업그레이드 브랜치의 base>
<이전 버전으로 설치>
<빌드 → 전수 실행>
```

base를 맞추는 것이 핵심이다. 그 사이 다른 작업이 머지됐으면 그 변경분이 차이에 섞여 들어간다. 업그레이드 브랜치의 부모 커밋을 그대로 쓴다.

대조는 숫자가 아니라 **집합**으로 한다.

- 양쪽에서 모두 실패 → 기존 결함. 업그레이드 무관
- 한쪽에서만 실패 → 후보. 다만 아직 결론이 아니다
- 후보를 **단독으로 다시 실행**한다. 전수에서만 빨갛고 단독으로 통과하면 병렬 부하 플레이크다

플레이크를 걷어내려면 병렬을 끄고(`--workers=1`) 재시도도 끈다(`--retries=0`). 재시도가 켜져 있으면 결정적 실패와 간헐 실패가 같은 "flaky" 칸에 섞인다.

## 이 과정이 남기는 것

기준선 런은 업그레이드 판정용이지만, 부산물로 **그 스위트의 만성 결함 목록**이 나온다. "원래 빨갰다"로 넘기지 말고 각 건의 에러를 실제로 읽어 축을 가르면(계약 변경 / 앱 결함 / 스펙 기대 오류 / 픽스처 오염) 그것대로 정리할 거리가 된다.

## 한 걸음 더

이 대조가 필요한 이유의 절반은 **e2e가 CI 게이트가 아니기 때문**이다. PR마다 전수가 돌면 깨진 시점이 커밋 단위로 특정돼 이런 사후 대조가 필요 없다. 게이트를 못 붙이는 사정이 있다면(테스트 계정 동시성, 실행 시간 등) 최소한 야간 스케줄이라도 두는 편이 낫다 — 다음 날 아침에 아는 것과 몇 주 뒤에 아는 것은 다르다.
