# Figma Desktop MCP는 페이지가 로드돼야 노드를 찾는다 — "No node could be found"는 노드 부재가 아닐 수 있다

Figma Desktop 앱 기반 MCP(`get_metadata`·`get_design_context`)로 노드 ID를 조회할 때, **대상 파일이 활성 탭이어도 그 노드가 속한 페이지가 앱에서 로드된 적이 없으면** `No node could be found for the provided nodeId` 에러가 난다. Figma는 페이지 단위 lazy loading이라, 열어본 적 없는 페이지의 노드는 데스크탑 앱 메모리에 없다.

## 왜 위험한가

에러 메시지가 "노드가 없다"고 말하기 때문에, 문서에 기록된 노드 앵커가 실제로는 멀쩡한데도 **시안이 재구성돼 노드가 삭제·이동됐다는 오판**으로 이어지기 쉽다. 실제 겪은 증상:

- 문서에 적힌 프레임 노드 다수가 조회 실패 → "노드 드리프트" 가설 수립
- 섹션 노드는 조회되는데 **자식이 0개**로 내려옴 → "내용물이 이동된 흔적"처럼 보여 가설이 강화됨
- 스크린샷 요청은 **빈 이미지**로 반환 → 오판을 한 번 더 굳힘

세 증상 모두 실제 원인은 하나 — 그 페이지를 앱에서 아직 열지 않았다는 것. 해당 페이지를 한 번 열자(또는 그 페이지의 아무 노드나 새로 탐색하자) 같은 노드 ID가 전부 정상 조회됐다.

## 부수 함정 — 검증 에이전트의 조용한 후퇴

노드 조회가 실패하면 LLM 검증 에이전트는 실측 대신 **문서 기반 추론으로 조용히 후퇴**해서 ✅ 판정을 낼 수 있다. 이 판정은 픽셀 실측이 아니므로 신뢰하면 안 된다. 검증 프롬프트에 "실측 실패는 실측 불가로 보고하고, 문서 추론으로 대체하지 말 것"을 명시해야 판정의 신뢰가 선다.

## 교훈

1. `No node could be found`를 보면 노드 삭제를 결론 내리기 전에 **그 페이지를 데스크탑 앱에서 열었는지부터** 확인한다.
2. 같은 파일에서 어떤 노드는 되고 어떤 노드는 안 되면, 파일 문제가 아니라 **페이지 로드 차이**를 의심한다.
3. 섹션은 조회되는데 자식 0개·빈 스크린샷도 같은 원인일 수 있다 — 이동·삭제의 증거로 읽지 않는다.
