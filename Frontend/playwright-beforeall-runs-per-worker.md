# `beforeAll` 은 파일당 한 번이 아니라 워커당 한 번이다

삭제 테스트가 간헐적으로 이렇게 죽었다.

```
Expected: 1
Received: 2
  > await expect(contactRows(page)).toHaveCount(1);
```

소모용 데이터를 `beforeAll` 에서 하나 만들고, 그 이름으로 검색해 1건이 나오는지 보는 테스트였다. 이름에는 실행마다 다른 랜덤 접두사가 붙는다.

```js
const PREFIX = runPrefix('CTROWDEL');   // CTROWDEL + 랜덤 6글자

test.beforeAll(async () => {
  [victim] = await createDisposableContacts(be, token, companyId, [PREFIX]);
});
```

랜덤이 겹칠 확률은 무시할 만하다. 그런데 2건이 나온다.

## 실제로 서버에 뭐가 있는지 봤다

```
876  CTROWDELAGBCRF   ← 같은 접두사
877  CTROWDELAGBCRF   ← 같은 접두사
875  CTROWDELHZMDVQ   ← 다른 실행의 잔여
```

**같은 접두사로 두 건이 만들어져 있었다.** 랜덤 충돌이 아니다.

## `beforeAll` 의 범위는 파일이 아니라 워커다

Playwright 는 `fullyParallel: true` 면 **한 파일의 테스트들도 여러 워커에 나눠 보낸다.** 그리고 `beforeAll` 은 그 파일의 테스트를 받은 **워커마다** 실행된다.

파일에 테스트가 3개 있고 2개 워커에 흩어지면:

```
워커 A: beforeAll 실행 → 데이터 1건 생성 → 테스트 1, 2 실행
워커 B: beforeAll 실행 → 데이터 1건 생성 → 테스트 3 실행
```

`PREFIX` 는 모듈 최상위라 워커마다 다시 평가되는데도 같은 값이 나온 건, 두 워커가 **같은 시드로 시작한 난수**를 썼기 때문이다. 어느 쪽이든 결론은 같다 — **생성 지점이 테스트 실행 단위와 어긋나 있었다.**

문서화된 동작이다. 다만 이름이 `beforeAll` 이라 "전부에 대해 한 번" 으로 읽히고, 로컬에서 워커 1개로 돌리면 절대 안 드러난다.

## 두 가지 처방

**① 실행 단위를 맞춘다** — 파일을 한 워커에 묶는다.

```js
test.describe.configure({ mode: 'serial' });
```

**② 생성을 테스트 안으로 옮긴다** — 테스트마다 자기 데이터를 만든다. 격리는 더 확실하지만 생성 비용이 테스트 수만큼 붙는다.

공유 자원(외부 DB·계정)을 쓰면 ①이 낫다. 순수 픽스처면 ②가 낫다.

## 잔여가 다음 실패를 부른다

같이 발견한 게 하나 더 있었다. 위 `875` 는 **이전 실행의 잔여**였다.

소모용 데이터를 지우는 경로가 삭제 테스트 자신뿐이었다. 그 테스트가 실패하면 데이터가 남고, 남은 데이터가 다음 실행의 검색 결과를 다시 흔든다 — **한 번 실패하면 계속 실패한다.**

```js
test.afterAll(async () => {
  if (!victim) return;
  await deleteContact(victim.id);   // 테스트가 실패해도 돈다
});
```

정리를 테스트 본문에 두면 그 테스트가 초록일 때만 청소된다. 청소는 **실패해도 도는 자리**에 둬야 한다.

## 검증 수단도 함께 골라야 한다

고친 뒤 `--repeat-each=5 --retries=0` 으로 확인했다. 이 파일은 통과했는데, 옆 파일에 같은 방법을 쓰니 5개 중 4개가 깨졌다.

그 파일의 테스트가 **공유 데이터의 이름을 바꿨다 되돌리는** 구조였기 때문이다. 5개를 병렬로 돌리면 서로의 전제를 무너뜨린다. 스펙 결함이 아니라 **검증 수단이 대상과 안 맞는** 것이다.

상태를 바꾸는 테스트에는 `--repeat-each` 대신 **순차 반복**(같은 명령을 여러 번)을 쓴다.

정리하면 — **`beforeAll` 이 보장하는 건 "테스트들보다 먼저" 지 "딱 한 번" 이 아니다.**
