# Server Action 을 가로채는 테스트는 빌드마다 ID 를 다시 읽어야 한다

Playwright 로 Server Action 응답만 바꿔 화면을 그리려면 요청을 함수 이름으로 골라야 한다. 그런데 요청에는 함수 이름이 없다. `POST` 의 `Next-Action` 헤더에 불투명한 ID 만 실려 온다.

ID 를 이름으로 바꾸는 표는 빌드 산출물의 `server-reference-manifest.json` 이다 (`node[<id>].exportedName`).

## 함정

이 표는 빌드마다 따로 생긴다 (Next.js 16.3 기준).

| 빌드 | 매니페스트 경로 |
|---|---|
| `next dev` | `.next/dev/server/server-reference-manifest.json` |
| `next build` | `.next/server/server-reference-manifest.json` |

같은 프로젝트의 두 매니페스트를 대조해 봤다. 이름이 같은 액션 200개 중 **ID 가 같은 것은 0개**였다. Next.js 15 부터 액션 ID 는 추측할 수 없는 값이고 빌드마다 다시 계산된다.

그래서 dev 매니페스트를 하드코딩한 스펙은 prod 빌드 서버에 붙으면 이렇게 된다.

- ID 를 이름으로 바꾸지 못한다.
- 스텁이 끼어들지 않고 실제 응답이 그대로 지나간다.
- 테스트는 에러 없이 "다른 화면"을 그린다. 실패 지점이 스텁이 아니라 그 뒤의 화면 단언이라서, 원인을 데이터 쪽에서 찾게 된다.

## 대응

- 매니페스트는 지금 떠 있는 서버의 빌드 모드에 맞는 경로에서 읽는다. 아니면 해당 스펙을 실행할 모드를 하나로 고정한다(dev 전용 스크립트 등).
- ID 를 상수로 박지 않는다. 런타임에 이름으로 조회한다.
- 스텁이 실제로 걸렸는지(매칭 0건이면 실패)를 단언해 두면 조용히 지나가지 않는다.

## 참고: 응답 바꾸기

응답 본문은 RSC 스트림이다. 관찰한 모양은 첫 줄이 헤더이고, `1:` 로 시작하는 줄이 액션의 반환값이었다. 그래서 `route.fetch()` 로 실제 응답을 받은 뒤 첫 줄을 남기고 `1:${JSON.stringify(data)}` 로 바꿔 `route.fulfill` 하면 클라이언트가 그 값을 반환값으로 받는다.

이 스트림 형식은 Next.js 내부 구현이라 버전에 따라 바뀔 수 있다.
