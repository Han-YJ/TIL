# RSC + React Query: 클라이언트 소유 쿼리는 URL 갱신도 shallow여야 한다

목록 데이터를 서버 페이징(TanStack Query + Server Action queryFn)으로 전환했는데, 검색어가 URL에는 반영되면서 **화면은 이전 전체 목록을 계속 보여주는** 결함을 만났다. 원인은 데이터가 아니라 **URL 상태 갱신 모드**였다.

## 증상과 격리 과정

- 검색 실행 → URL `?q=...` 반영 → 그러나 테이블은 전체 목록 그대로
- ① 같은 파라미터로 백엔드 직접 호출 → 정상(0건). 서버 원인 기각
- ② URL 직접 진입(`/list?q=...`) → 정상. **화면 내 전환(입력→URL 갱신)만 실패**로 격리
- ③ 네트워크 추적 → RSC 재렌더는 발생하고 서버 prefetch도 새 파라미터로 정상 조회하는데, **클라이언트 fetch(서버액션 POST)가 아예 발생하지 않음**

## 원인

필터 입력이 nuqs `shallow: false`(RSC 라운드트립 모드)로 남아 있었다. 이 경로에서는:

1. URL 변경 → Next 라우터 네비게이션(트랜지션) → 페이지 RSC 재렌더 + 새 파라미터로 prefetch/dehydrate
2. 그런데 새 쿼리 키의 하이드레이션이 클라이언트 캐시에 **병합되지 못하는 구멍**이 생길 수 있고
3. 클라이언트 observer는 캐시 미스인데도 fetch를 시작하지 않아, `keepPreviousData`가 이전 키의 데이터를 계속 노출한다

즉 "URL이 바뀌면 하이드레이션이 알아서 온다"는 가정이 깨진다. RSC 라운드트립 하이드레이션은 **첫 페인트용**이지, 클라이언트 소유 쿼리의 파라미터 전환 채널로 신뢰할 수 없다.

## 원칙

데이터 소유권이 클라이언트 React Query로 넘어간 화면에서는 **URL 상태 갱신도 세트로 shallow(`shallow: true`)로 넘긴다**:

- URL은 상태 직렬화만 담당 (라우터 네비게이션 없음)
- 조회는 클라이언트 쿼리 키 변경 → queryFn(서버액션) fetch가 담당
- RSC prefetch는 첫 진입의 캐시 적중용으로만 유지

반대로 RSC가 데이터를 소유하는 화면(props로 내려주는 구조)은 `shallow: false`가 맞다. **데이터 regime을 이관하면 URL 갱신 모드까지 함께 이관해야 한다** — 한쪽만 옮기면 위처럼 조용히 깨진다.

## 배운 것

이 결함은 타입 체크·단위 테스트를 전부 통과했고, "검색 0건이면 빈 상태가 뜬다"는 e2e 시나리오가 잡아냈다. 상태 소유권이 걸린 전환 작업에서는 happy path보다 **0건/경계 시나리오가 회귀 감지력이 높다**.
