# 검색 입력이 붙은 목록은 menu 가 아니다

디자인 시안이 "드롭다운 메뉴"라고 부르길래 메뉴 위젯 위에 조립하려다 멈췄다. 상단에 검색 입력이 붙어 있었기 때문이다.

## 무슨 일이 벌어지나

메뉴 위젯(`role="menu"`)에는 **typeahead** 규약이 딸려 온다. 사용자가 글자를 치면 그 글자로 시작하는 항목으로 포커스가 점프하는 동작이다. 파일 탐색기에서 `ㅅ`을 누르면 "사진" 폴더로 가는 그것이고, 메뉴 구현체들은 이걸 기본으로 넣는다.

그래서 메뉴 안에 `<input>`을 두면 충돌한다. `ㄱ`을 치면 입력창에 들어가야 하는데 위젯이 그 키를 가로채 "ㄱ으로 시작하는 항목"으로 포커스를 옮긴다. 글자는 안 써지고 커서는 튕겨 나간다.

## 규약 자체가 금지한다

typeahead 를 억지로 끈다고 해결되지 않는다. W3C APG 의 menu/menubar 패턴은 메뉴의 자식으로 **`menuitem` · `menuitemcheckbox` · `menuitemradio` 셋만** 허용한다. textbox 는 그 목록에 없다. 즉 키 충돌은 증상이고, 원인은 애초에 성립하지 않는 조합을 만든 것이다.

같은 문서가 대안도 정해두고 있다 — 검색으로 좁히는 목록은 **`combobox` + `listbox`** 다.

| | menu | combobox + listbox |
|---|---|---|
| 타이핑 | typeahead(포커스 점프) | 검색어 입력 |
| 항목 포커스 | 실제 포커스 이동 | `aria-activedescendant` 로 가리킴 |
| 텍스트 입력 | 불가 | 그게 본체 |

listbox 쪽에서 항목이 탭 순서에 없는 건 의도다. 포커스는 입력창(또는 컨테이너)에 두고, 활성 항목은 `aria-activedescendant` 로 가리킨다. 8개짜리 목록에서 확정 버튼까지 가는 데 탭을 9번 누르지 않아도 되는 이유가 이것이다.

## 진짜 교훈은 축이 두 개라는 것

디자인 시안이 그 컴포넌트를 뭐라고 부르든 그건 **시각 스펙**이다. 어떤 위젯으로 구현하느냐는 **별개 축**이고, 접근성 규약이 결정한다.

- 폴더 이름·컴포넌트 이름은 디자인 시스템을 따라도 된다
- 그 안에서 어떤 프리미티브를 쓰는지는 role 이 결정한다

"Dropdown menu" 라는 이름은 생김새를 말할 뿐 위젯 종류를 말하지 않는다. 이름을 보고 프리미티브를 고르면 규약을 어긴 채로 시작하게 된다.

## 판별 기준

목록 안에 **텍스트를 입력받는 자리가 하나라도 있으면** menu 가 아니다. 검색창이든 인라인 편집이든 마찬가지다.

반대로 액션만 나열하는 목록(복사·이름 바꾸기·삭제)이면 menu 가 맞고, typeahead 도 공짜로 얻는 이득이다.
