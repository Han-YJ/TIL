# 로딩 지연을 플래그 하나에 걸면 빈 상태가 샌다

목록 스켈레톤이 빠른 응답에서 번쩍이는 게 거슬려서 **지연 표시**를 걸었다. 200ms 안에 데이터가 오면 스켈레톤을 아예 띄우지 않는 흔한 처방이다.

그런데 그 200ms 동안 **"조건에 맞는 항목이 없어요" 빈 상태가 번쩍였다.** 스켈레톤 깜빡임을 없애려다 더 나쁜 걸 만들었다.

## 왜 그런가

표 컴포넌트는 보통 이렇게 생겼다.

```tsx
{loading ? <SkeletonRows /> : rows.length === 0 ? emptyState : rows.map(...)}
```

`loading` 이 **두 가지 일을 동시에** 하고 있다.

1. 자리표시 행을 그린다
2. 빈 상태를 막는다

지연을 `loading` 에 걸면 둘 다 지연된다. 그 사이 상태는 `loading = false` · `rows = []` 이고, 이건 **"다 불러왔는데 0건"** 과 구분되지 않는다. 그래서 빈 상태가 뜬다.

데이터가 없는 상태에는 사실 두 종류가 있는데 플래그 하나로 뭉뚱그린 게 원인이다.

- **아직 모른다** (요청 중)
- **없는 걸 안다** (0건 응답)

## 대응

두 축을 분리한다. **"데이터가 아직 아님" 은 즉시**, **"자리표시를 그릴지" 만 지연**시킨다.

```tsx
// loading = 데이터가 아직 아님 → 지연 없이 즉시 (빈 상태를 막는 역할)
// rowCount = 자리표시 행 수 → 여기에만 지연을 건다
<Table loading={isLoading} loadingRows={showSkeleton ? 8 : 0} />
```

`loadingRows={0}` 이면 본문이 그냥 빈 칸으로 남는다. 헤더·필터·푸터는 서 있고 데이터 영역만 잠깐 비는데, 200ms 라 눈에 띄지 않는다. 빈 상태 문구는 `loading` 이 막고 있어 새지 않는다.

## 지연만으로는 부족하다

지연 200ms 만 걸면 구멍이 하나 남는다 — **210ms 에 응답이 오면 스켈레톤이 10ms 번쩍인다.** 지연 직후 도착이 오히려 가장 나쁜 케이스다.

그래서 **최소 표시 시간**이 같이 필요하다. 한번 뜨면 400ms 는 유지한다.

```ts
// active 가 delay 이상 유지될 때만 true, 한번 true 가 되면 minDuration 동안 유지
useDelayedFlag(isLoading, 200, 400)
```

해제를 즉시로 두면(최소 표시 시간 0) 지연만 있는 것과 같아 위 구멍이 그대로 남는다. 반대로 최소 표시 시간만 두고 지연이 없으면 빠른 응답에서 400ms 를 억지로 기다리게 된다. **둘은 세트다.**

## 곁들여 — 자리표시는 그림이 아니다

이 작업의 출발점은 "스켈레톤이 성의 없어 보인다" 였는데, 정작 문제는 회색 막대의 생김새가 아니었다.

자리표시를 **별도 컴포넌트**로 그리고 있었고, 그러다 보니 행 높이가 32px(실제 64px), 컬럼이 4개(실제 6개), 헤더행·구분선·페이지네이션이 아예 없었다. 8행이 ~256px 를 차지하다 데이터가 오면 512px + 헤더 + 푸터가 된다. **로딩이 끝나는 순간 화면이 두 배로 튀었다** — 자리표시가 막으려던 바로 그 현상이다.

별도 컴포넌트로 그리면 치수는 **반드시** 어긋난다. 컬럼이 하나 늘 때 두 곳을 같이 고칠 사람은 없기 때문이다. 표 컴포넌트가 자기 로딩을 직접 그리게 해서 헤더·트랙·행 높이·구분선·푸터를 데이터 렌더와 **공유**시키는 게 유일하게 안 어긋나는 구조다.

그리고 하나 더 — 타이틀·탭 라벨·열 라벨처럼 **데이터 없이도 아는 값**을 회색으로 덮고 있었다. 아는 걸 가리면 "아무것도 안 왔다"로 읽힌다. 체감 지연을 만드는 건 스켈레톤의 개수가 아니라 **회색이 덮은 면적**이다.

## 판별 기준

- 로딩 플래그가 **빈 상태를 막는 역할까지 겸하고 있으면** 지연을 그 플래그에 걸지 않는다
- 지연을 넣을 땐 **최소 표시 시간을 세트로** 넣는다
- 자리표시 치수가 실제와 따로 관리되고 있으면, 예쁘게 다듬기 전에 **한 곳에서 나오게** 만든다
